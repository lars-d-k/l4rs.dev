Data Technologies - Test Prep Summary

Only core topics are included. Keep this as a fast recall sheet.

Basic SQL (W1)

Relational databases

  • Tables + PK/FK + constraints enforce consistency; transactions follow ACID.
ALTER TABLE enrollments
ADD CONSTRAINT fk_course FOREIGN KEY (course_id) REFERENCES courses(id);

Select

  • Core query flow: SELECT -> FROM -> WHERE -> GROUP BY -> HAVING -> ORDER BY.
SELECT department, COUNT(*)
FROM courses
GROUP BY department
HAVING COUNT(*) > 5;

Joins

  • INNER = matches only, LEFT = all left + matches, FULL = all rows from both.
SELECT s.name, c.name
FROM students s
JOIN enrollments e ON e.student_id = s.id
JOIN courses c ON c.id = e.course_id;

Data (insert/update/delete)

  • Write operations are easy to break with missing WHERE; be explicit.
UPDATE students SET email = 'new@mail.com' WHERE id = 42;

Advancing

  • Use CASE, subqueries, UNION, COALESCE for compact reporting queries.
SELECT name, CASE WHEN grade >= 10 THEN 'pass' ELSE 'fail' END AS result
FROM exams;

Advanced SQL (W2)

Introduction

  • Goal: write readable, composable SQL for analytics and complex business logic.

Views

  • View = saved query (virtual table), useful for reuse and access control.
CREATE VIEW active_students AS
SELECT id, name FROM students WHERE active = true;

CTE

  • WITH makes multi-step queries clearer; recursive CTE handles hierarchies.
WITH recent AS (
  SELECT * FROM enrollments WHERE enrolled_at >= CURRENT_DATE - INTERVAL '30 days'
)
SELECT COUNT(*) FROM recent;

Window functions

  • Compute rank/running totals without collapsing rows.
SELECT name, salary,
       RANK() OVER (ORDER BY salary DESC) AS salary_rank
FROM employees;

Transactions

  • Use BEGIN/COMMIT/ROLLBACK for atomic multi-step changes.
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;

JSON

  • PostgreSQL JSON/JSONB lets you query semi-structured fields directly.
SELECT details->>'level' AS level
FROM courses
WHERE details->>'track' = 'data';

Full-text

  • to_tsvector + to_tsquery beats LIKE for word search and ranking.
SELECT title
FROM articles
WHERE to_tsvector('english', body) @@ to_tsquery('database & index');

Database Design (W3)

Introduction

  • Design first, then implement: conceptual -> logical -> physical.

Conceptual design (ERD)

  • Model entities, attributes, cardinalities (1:1, 1:N, M:N) before SQL.

Physical design

  • Choose correct types and constraints early to prevent bad data.
CREATE TABLE students (
  id SERIAL PRIMARY KEY,
  email VARCHAR(255) UNIQUE NOT NULL
);

Relations

  • M:N becomes a junction table with two foreign keys.
CREATE TABLE enrollment (
  student_id INT REFERENCES students(id),
  course_id  INT REFERENCES courses(id),
  PRIMARY KEY (student_id, course_id)
);

Altering tables

  • ALTER TABLE evolves schema safely in steps.
ALTER TABLE students ADD COLUMN birth_date DATE;

Procedures and triggers

  • Trigger = auto action on insert/update/delete; use sparingly for invariants/audit.
CREATE TRIGGER set_updated_at
BEFORE UPDATE ON students
FOR EACH ROW EXECUTE FUNCTION touch_updated_at();

Deleting tables

  • DROP TABLE ... CASCADE removes dependencies too; use carefully.
DROP TABLE IF EXISTS enrollment CASCADE;

Security

  • Apply least privilege with roles and grants.
GRANT SELECT ON students TO app_reader;
REVOKE INSERT, UPDATE, DELETE ON students FROM app_reader;

Normalisation (W4)

Introduction

  • Normalization reduces redundancy and update bugs.

Anomalies

  • Insert/update/delete anomalies are the reason normalization exists.

Dependencies

  • Functional dependency A -> B means A determines B.

Normal forms (test scope)

1NF (0NF -> 1NF)

  • No repeating groups; all attributes atomic.
-- Bad: student(courses = 'DB,AI')
-- Good: enrollment(student_id, course_id)

2NF

  • 1NF + no partial dependency on part of a composite key.
-- Bad (partial dependency): PK = (student_id, course_id)
-- instructor_name depends only on course_id
enrollment(student_id, course_id, instructor_name)

-- Good (2NF): split course-level attributes
enrollment(student_id, course_id)
courses(course_id, instructor_name)

3NF

  • 2NF + no transitive dependency between non-key attributes.
-- Bad (transitive dependency): student_id -> department_id -> department_name
students(student_id, department_id, department_name)

-- Good (3NF): move department details out
students(student_id, department_id)
departments(department_id, department_name)

BCNF

  • Stronger 3NF: every determinant must be a candidate key.
-- Bad (not BCNF): in a course-room-timeslot table,
-- room,timeslot -> course (so room,timeslot is a determinant but not a candidate key)
schedule(course, room, timeslot)

-- Good (BCNF): decompose by determinants
course_schedule(course, room, timeslot)
room_slot_assignment(room, timeslot, course)

Higher normal forms

  • For this test, stop at BCNF (4NF-6NF not required).

Performance

  • More normalization = less redundancy, but often more joins.

Optimalisation (W5)

Introduction

  • Performance work is mostly: better indexes, better plans, less data scanned.

Indexing

  • Index columns used in WHERE, JOIN, ORDER BY; avoid over-indexing writes.
CREATE INDEX idx_orders_customer_created
ON orders(customer_id, created_at DESC);

Materialized Views

  • Precomputed query results; fast reads, requires refresh.
CREATE MATERIALIZED VIEW mv_sales AS
SELECT product_id, SUM(amount) AS total
FROM sales
GROUP BY product_id;

Partitioning

  • Split very large tables by date/list/hash for pruning.
CREATE TABLE logs (
  id BIGSERIAL,
  created_at DATE NOT NULL
) PARTITION BY RANGE (created_at);

Query optimization

  • Read execution plans and rewrite expensive joins/filters first.
EXPLAIN ANALYZE
SELECT * FROM orders WHERE customer_id = 10;

Caching

  • Cache hot reads (Redis/app cache), keep TTL/invalidation strategy explicit.

Key Value Databases (W6)

Introduction

  • Key-value stores optimize ultra-fast lookup by key.

Types of NoSQL databases

  • Know differences: key-value, document, graph (different query strengths).

Working with key-value databases

  • Redis basics: strings, hashes, lists.
SET user:1 "Alice"
HSET product:42 name "Laptop" price 899

Working with sets

  • Sets are unique unordered values; useful for tags/membership.
SADD course:db students:1 students:2
SINTER course:db course:sql

Working with numeric values

  • Atomic counters with INCR/DECR.
INCR page:home:views

In-memory databases

  • Very fast, but persistence config (RDB/AOF) matters for durability.

Redis as message bus

  • Pub/Sub for live events; Streams/queues when persistence is needed.
PUBLISH alerts "exam-started"

Document Databases (W7)

Introduction

  • Document model (JSON-like) supports flexible schema and nested data.

Working with documents

  • CRUD + projections + operators are MongoDB essentials.
db.products.find({ price: { $gt: 500 } }, { name: 1, price: 1, _id: 0 })

Schema-less in MongoDB

  • Schema-less is flexible, not schema-free; validate critical fields.
db.createCollection('orders', {
  validator: { $jsonSchema: { required: ['customerId', 'total'] } }
})

Schema design principles

  • Embed for read-together data, reference for shared/high-growth data.

Indexes

  • Use single/compound indexes based on real query patterns.
db.orders.createIndex({ customerId: 1, createdAt: -1 })

Aggregation

  • Pipeline stages: $match, $group, $project, $sort.
db.orders.aggregate([
  { $group: { _id: '$customerId', total: { $sum: '$total' } } },
  { $sort: { total: -1 } }
])

Graph Databases (W8)

Introduction

  • Graph DBs model relationships as first-class citizens (nodes + edges).

Working with graph queries

  • Cypher MATCH pattern queries are key exam skill.
MATCH (s:Student)-[:ENROLLED_IN]->(c:Course)
RETURN s.name, c.name;

Properties on relationships

  • Store context on edges (e.g., rating, since, weight).
MATCH (:User {id: 1})-[r:RATED]->(m:Movie)
RETURN m.title, r.score;

Modify relationships

  • CREATE always inserts; MERGE is idempotent upsert-like behavior.
MERGE (a:User {id: 1})-[r:FOLLOWS]->(b:User {id: 2})
ON CREATE SET r.since = date();

Databases Security and Privacy (W9)

Introduction

  • Security = layered controls: auth, authorization, encryption, auditing.

Access Control

  • RBAC: grant by role, not by user; always least privilege.
CREATE ROLE analyst;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO analyst;

Row Level Security

  • RLS filters rows per user/tenant at DB level.
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON orders
USING (tenant_id = current_setting('app.tenant_id')::int);

Privacy and anonymization

  • Apply minimization + masking/pseudonymization for PII and compliance.
SELECT LEFT(email, 2) || '***@***' AS masked_email FROM users;
